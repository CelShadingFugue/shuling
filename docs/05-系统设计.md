# 05 · ourApp 系统设计（v0.2 目标形态）

> 这份文档只解决一件事：**在加交互之前，把对象和文件定下来。**
> 现在每加一个交互，都是在给"还没有数据模型"的界面打补丁；补丁多了，下一次重构就是重写。
> 交互细节在 [06-交互设计](06-交互设计.md)，优先级和迭代计划在 06 的最后一节。

---

## 1. 对象总表

| 对象 | 一句话职责 | 实例数 | 存在哪 | 同步 |
|---|---|---|---|---|
| **OurApp** | 每个人电脑上跑的那个管家进程：装配、同步、分发 | 1 / 台 | 内存 | — |
| **WebObject** | 所有界面的宿主：时间线视图、负责域视图、设置 | 1 | 内存 | 否 |
| **ChatObject** | 聊天与通知的对话流（本轮只设计） | 1 | `chat/*.md` | 是 |
| **BoardObject** | 公共分工看板，时间线的真身 | 1 | `board/` | 是 |
| **CalendarObject** | 日历：刻度体系、视口、当前时刻、缩放级别 | 1 | 视图态 | 否 |
| **TaskGroup** | 主任务：一条主线 / 一个组，记录名字与子任务 | N | `groups/{id}.json` | 是 |
| **Task** | 子任务：时间线上那张卡，有 readme、起止、lane、pin | N | `tasks/{id}.json` + `.md` | 是 |
| **Deliverable** | 交付物：这个任务要交的东西 + 验收标准 + 状态 | N | `deliverables/{taskId}.json` | 是 |
| **DutyArea** | 负责域：人 ↔ 任务 的登记处（含 owner/participant 角色） | 1 | `duty.json` | 是 |
| **Member** | 一个人：邮箱 + 参与的项目 + 角色 | 1 本地 + N 远端 | `members/{id}.json` | 是 |
| **MailObject** | 这个人的消息箱，接云端推送 | 1 | 本地缓存 | 只收 |
| **ProjectObject** | 这个人参与的项目列表与角色 | 1 | 随成员 | 是 |

**一句话读法**：OurApp 是进程，Board 是数据，Web 是脸，Member 是人，Task/Group/Deliverable 是被分的活。

## 2. 对象关系

```
Member (本机那个人)
 ├─ MailObject         收推送、收别人 @ 我
 └─ ProjectObject      我参与的项目 + 我的角色（owner / participant）

OurApp (单例)
 ├─ WebObject          渲染；只读模型，只发意图（intent）
 ├─ ChatObject ──── chat/log-YYYY-MM.md   （append-only 长文件）
 └─ BoardObject
      ├─ CalendarObject      刻度/视口/now（视图态，不落盘）
      ├─ DutyArea            Member × Task 多对多
      ├─ TaskGroup[]         ─┬─ Task[]           组合关系，子任务不能脱离组存在
      │                        ├─ Deliverable     1 : 1
      │                        ├─ readme.md       1 : 1
      │                        └─ Participation   N : N（引用 DutyArea）
      └─ Milestone[]        验收节点（虚线），只读，来自申请书
```

三条硬约束：

1. **Task 是 TaskGroup 的成员类**（你说的"从这反推"是对的）。`task.groupId` 不可为空；移动任务 = 改 `groupId`，不是复制。
2. **Participant 不是 Task 的字段，而是 DutyArea 里的边**。否则"一个人参与了哪些事"要扫全表。
3. **Calendar 是视图态**。缩放、滚动、折叠、当前时刻都不进文件——不同步，也不产生 diff。

## 3. 文件布局

同步区是一个目录，一个人一份镜像，云端是同一份：

```
board/
  groups/A.json          {id,name,color,order,pinned,collapsed}
  tasks/A1.json          {id,groupId,name,start,end,lane,pinned,order,color,createdBy}
  tasks/A1.md            这个任务的 readme（可空）
  deliverables/A1.json   {taskId,title,criteria,status}
  duty.json              {"A1":[{"memberId":"1","role":"owner"}],"A1:2":...}
  members/1.json         {id,name,short,color,mail[]}
chat/
  log-2026-11.md         一行一条，append-only
meta/
  rev.json               {path: rev}  云端对齐用
```

**一对象一文件**是刻意的：一次拖动只改 `tasks/A1.json` 一个文件，冲突面积最小。
**JSON 每字段一行、键排序**，这样 git 也能做行级合并，不会因为格式化差异整文件冲突。

## 4. 三种状态，别混

| 状态 | 例子 | 落盘 | 同步 | 进 diff |
|---|---|---|---|---|
| 模型态 | 任务的起止、lane、pin、职责 | 是 | 是 | 是 |
| 视图态 | 缩放级别、滚动位置、折叠的组、当前时刻开关 | localStorage | 否 | 否 |
| 会话态 | 正在拖的那个影子、批量面板开没开、框选框 | 否 | 否 | 否 |

这条线一旦模糊，后面会出现"我这边折叠了，别人那边也折叠了"这种鬼问题。

## 5. 同步协议

### 5.1 本地：谁产生变更

```
Web  →  intent（拖到某刻度、pin、加参与人）
OurApp → BoardObject.apply(intent)        // 校验 + 生成 Command
       → BoardObject.diff(sinceRev)       // 差异文本（JSON Patch + 一行摘要）
```

「差异文本」是两份东西：

- **机器读的**：`[{op:"replace", path:"/tasks/A1/start", value:"2027-03-01"}]`
- **人读的**：`A1 延迟打点 从 3/1 挪到 3/8（冯）`

前者给云端对齐，后者直接进聊天流。

### 5.2 远程：一次上交

```
POST /sync/upload
  { baseRev: 42, changes: [ {path, patch, summary} ] }
→ 200 { rev: 43 }                       对齐成功
→ 409 { rev: 43, theirs: [ {path, patch} ] }   有冲突，见 5.3
```

### 5.3 云端对齐与推送

```
云端：按 path 串行。baseRev 相同 → 合并；不同 → 逐字段三方合并
      合得上 → 新 rev，广播
      合不上 → 两边都写进文件，标 conflict:true，广播带 conflict 标记
各端：WebSocket 收到 {rev, changes} → OurApp.applyRemote → Web 增量更新
```

### 5.4 冲突策略（必须先定，不能事后补）

| 情况 | 处理 |
|---|---|
| 两人改不同任务 | 直接合 |
| 两人改同一任务的不同字段 | 字段级合 |
| 两人改同一任务的同一字段（都拖了 A1） | 保留两个值，界面出黄条："A1 时间刚被别人改过，用哪个？"，不自动选 |
| 一人删、一人改 | 以删为准，改的那端留一条"已删除"记录，可撤销 |

**不做自动 last-write-wins。** 静默覆盖是最伤信任的 bug，第二次发生就没人敢用了。

## 6. 不变式（代码任何时候都得成立）

| # | 不变式 | 为什么 |
|---|---|---|
| I1 | 任务必有父组；组删除时子任务随之删除或迁移，不许悬空 | 否则时间线渲染会炸 |
| I2 | 同一组内没有空 lane（压缩在每次提交前跑） | 否则组会越拖越高 |
| I3 | **pin 锁的是时间，不是行** | 否则"空行必须压缩"和"pin 不许动"直接打架 |
| I4 | 吸附在模型层完成，落盘的 start/end 一定是刻度值 | 否则渲染层和模型层各算一次，永远对不齐 |
| I5 | 所有修改走 Command，可撤销 | 复杂交互没有撤销就是灾难 |
| I6 | 视图态绝不进文件、不产生 diff | 见第 4 节 |
| I7 | 每个任务都有 readme 文件（可以是空文件） | 交互里要"跳转到 readme"，不能有空指针 |
| I8 | 复制粘贴产生新 id，不共享引用 | 否则改一个全变 |
| I9 | 每个对象有 id 和 rev | 没有 rev 就没法做增量同步 |

I3 是这一版最重要的设计决定。你提的"空行判断优先级高于 pin"，本质上是 pin 语义之争：
**pin = 这条任务的时间和它所在组的顺序被确定，不是"它在第几行"被确定。** 行永远由排版算法决定。

## 7. v0.1 → v0.2 的迁移清单

| 现在 | 目标 | 动作 |
|---|---|---|
| `data/index.js` 扁平 TASKS | TaskGroup ⊃ Task | 把 `line` 字段升级成 Group 对象 |
| `{taskId: [personId]}` | DutyArea 的边（带 role） | 加 role 字段 |
| 卡片 `row` 由渲染时算 | `lane` 存模型，提交前压缩 | 抽 `normalizeLanes()` |
| 无 Command | Command + UndoStack | 所有 mutation 走一层 |
| localStorage 整体存 map | 一对象一文件 + rev | 本地先用同一个目录结构存 |
| 无 Rev | `meta/rev.json` | 每次提交 +1 |

迁移顺序不能反：**对象 → 文件 → 命令 → 同步**。先做同步会把没定型的数据结构钉死在协议里。

## 8. 要你拍板的四件事

1. **时间精度**：任务要精确到小时吗？日级视图需要。定了才知道 `start` 是 `2027-03-01` 还是 `2027-03-01T09:00`。
2. **云端用什么**：GitHub 仓库 / 自建接口 / Supabase。决定 5.2 是走 HTTP 还是走 git push。
3. **聊天保不保**：如果换成 VS Code LiveShare，`ChatObject` 可以砍；但"留痕"没了，得另找地方记（比如每次同步自动写一条 summary 进 `chat/log`）。这个替代其实成本很低——**5.1 里那行"人读的摘要"本来就是为它准备的**。
4. **交付物粒度**：每个任务一个交付物，还是每条主线一个？建议后者，交付物数量会少一半。
