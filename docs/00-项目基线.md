## 1. 一句话

书桌上放一台能听、能看、会有身体反应的学伴机器人：孩子指着课本问"这里什么意思"，它看着那一页回答，并且用姿态和灯表达"我在想""我懂了""再试一次"。

## 2. 用户与场景（先钉死，防止功能发散）

| 项 | 定 |
|---|---|
| 谁 | 中小学生（小学高年级—初中），一个人在家写作业 |
| 什么时候用 | 卡住的那一刻：不会做、不想做、想有人陪 |
| 桌面条件 | 课本/练习册摊开、有台灯、有 WiFi |
| 明确不覆盖 | 课堂、多人、户外、考试、成人自学 |

场景越窄，演示越稳。评委问"凭什么相信能做出来"，答案是"因为这个场景我们只解决一件事"。

## 3. 能力的五个挂载点：以后加功能往这里挂

任何新想法，先回答一句：**它挂在第几层？**挂不上就不做。

| 层 | 能力 | 一句话验收 | 优先级 |
|---|---|---|---|
| **L0 骨架** | 能听会说 | 说一句话，3 秒内听到回答 | 必须，不可降级 |
| **L1 身体** | 状态反馈 | 思考/鼓励/困惑/庆祝 四种状态有可区分的动作+灯 | 必须，这是立项理由 |
| **L2 眼睛** | 看教材 | 指着一页问，10 次里对 8 次 | 必须，但允许降级 |
| **L3 教学** | 教学策略 | 追问、错题复习、苏格拉底式提示，至少 2 种跑通 | 加分 |
| **L4 产品** | 可复现 | 陌生人按 README 一小时装起来 | 作品集门槛 |

三条规则：

1. **L0 是演示路径，任何时候不能坏。** 任何改动提交前，先跑一遍 L0。
2. 新功能只能加在 L1–L3，而且必须能**在 30 秒内关掉**（配置项/开关）。演示时出问题可以回到纯语音。
3. L4 不是最后一个月才做，是从第一天做：每次提交都保证"别人还能装起来"这件事不退步。

## 4. 明确不做

写下来不是为了限制，是为了在会上有一句话能挡回去："这个在我们不做清单里，先记下来 v2 再谈。"

- 不自研唤醒词 / ASR / TTS 模型（一律用现成的）
- 不做本地大模型推理（API 或实验室服务，端侧只做前处理）
- 不追 OCR / 检测的 SOTA（场景约束下能用即可，这是申请表原话）
- 不做手机 App、小程序、账号体系、支付
- 不做量产级结构件（3D 打印够用）
- 不做跨天长时记忆（v1 只保留会话内上下文）
- **前半年（到 2027.2）不把 ESP32-S3 放进主线**（理由见第 6 节）

## 5. 四个可演示状态（对齐申请表的四阶段）

阶段是申请表已经报上去的，不改。但每一阶段结束的判据不是"做完了"，是"**能连续演**"。

| 时间 | 交付物 | 那三分钟怎么演 | 判据 |
|---|---|---|---|
| 2026.12–2027.02 | 软件内核 | 笔记本上：说话 → 回答，屏幕打出延迟分解 | 连演 5 轮不崩，延迟有数据 |
| 2027.03–2027.05 | 实体原型 | 盒子里：说话 → 回答 + 动作；拔网线会说"我断网了" | 连演 5 轮不崩，断电重启能自启 |
| 2027.06–2027.08 | v0.8 | 指着课本问，三个学习场景连演 10 分钟 | 试用 2–4 周，有 A/B 数据 |
| 2027.09–2027.11 | v1.0 | 别人拿仓库装起来；视频 + 报告 + 试用数据 | 陌生人 1 小时装通 |

"能跑一次"和"能连续演示"之间，差的是整个工程的量。这条判据要现在就跟组员说清楚。

## 6. 现在就该定的技术决策：主线用树莓派

**决策**：主线 = 树莓派（Linux / Python），负责“会想”的部分。舵机和灯优先走 I2C 的 PCA9685 驱动板（硬件产生 PWM）。ESP32-S3 不进主线，只做可选的“神经末梢”：按键、模拟量、低功耗待机。

**理由**

1. 我们的难点在**软件链路**（语音、检索、大模型、流式），不在微控制器的实时性。
2. Python 链路可以**先在 PC 上调通，再原样搬到 Pi**；换成 S3，整条链路要用 C 重写，还要在 512 KB 内存里塞 TLS + 音频编解码。
3. 组里三个零基础的同学，在 Linux 上装包看报错，和在 ESP-IDF 里配 FreeRTOS 任务，不是一个难度量级。

**代价（要提前认）**

- Linux 不是实时系统：如果直接让 CPU 生成 PWM，舵机会抖
- 功耗几瓦，要正经电源；开机 20–40 秒；SD 卡会坏，得留镜像
- 40 针只有 3.3V、每针十几 mA、没有模拟输入

### 【答·你写的三个问题】

> **“所以使用 ESP32 不就是为了打包解决硬件控制问题顺便提供无线通信功能吗？”**
>
> 对，这一点你说得比我原文准。ESP32 的价值不是替代树莓派，是替它干它干不好的事：可预测的 PWM、多路舵机、模拟输入（树莓派根本没有）、低功耗待机。但它也带来一个成本：要写 C 固件、维护一套串口协议。
>
> 而“PWM 会抖”还有更便宜的解法：PCA9685——一块十几块的 I2C 小板，硬件产生 PWM，不占 CPU，Python 直接能用。所以现阶段先用模块，等真需要“低功耗待机 / 无线遥控”时再上 ESP32。
>
> 一句话：**Pi 是大脑，ESP32 是神经末梢；能用模块解决的，先别写固件。**

> **“功耗几瓦、开机 20–40 秒、SD 卡会坏——没听懂”**
>
> - **功耗几瓦**：它是一台小电脑，要 5V/5A（Pi 5）或 5V/3A（Pi 4）。拿手机充电器凑合，摄像头 + WiFi 一起工作时会随机重启，然后你会以为是代码问题，查三天。
> - **开机 20–40 秒**：它是电脑，要启动 Linux。断电再来一次得等半分钟，所以必须做开机自启，不能等人 ssh 进去敲命令。
> - **SD 卡会坏**：SD 卡就是它的硬盘，突然断电容易写坏。所以要定期把整张卡备份成镜像，坏了十分钟重刷——这是 E 线的事。

> **“输入不都通过 ESP32 代理吗？？？”**
>
> 对。如果所有输入输出都走代理，那“3.3V / 十几 mA / 没有模拟输入”这三条就不成立了——树莓派只连一根 USB 或串口线（3.3V、几毫安，够用）。
>
> 我原文列的是“把传感器和舵机直接插在树莓派针脚上”那条路的问题。既然走代理 / 模块路线，这三条就该改写成：**前提是别直连**。
>
> 剩下真正躲不掉的只有一条：它是一台电脑，所以慢、费电、怕断电。

**缓解**

- 舵机/灯走 PCA9685（I2C 硬件 PWM），不占 CPU，抖动可接受
- 真要低功耗待机或无线遥控，再挂一颗 ESP32，接口定成串口协议——这就是“端内协同”，本身就是个能写进答辩的点
- 电源分两路：Pi 一路，舵机一路，共地

**关于群名**：现在叫“ESP32-S3 **且** 树莓派”。实际上不是两块板都写大程序——Pi 写逻辑，ESP32 最多写一百行驱动。但一个“且”字会让人以为两个都是主角，最后变成两套半成品。建议改成“树莓派主线 + ESP32 外设”，一个“或”字也行——申请书原文写的就是“或”。

## 7. 非功能指标：这才是"作品"和"作业"的差别

| 指标 | 目标 | 怎么证明 |
|---|---|---|
| 端到端延迟 | P50 < 2.0s，P90 < 3.5s | 分环节打点（采集/ASR/检索/LLM/TTS/播放），出报告 |
| 稳定性 | 连续 2 小时不重启 | 跑一夜，早上还在 |
| 可复现 | 新 SD 卡 → 能对话，≤ 60 分钟 | 找个没参与的人试一次，掐表 |
| 可观测 | 每轮对话有日志 | 时间戳、各环节耗时、token 数、错误码 |
| 降级 | 断网 10 秒内说人话 | 拔网线演示 |
| 隐私 | 原始音频不外传第三方（除自建服务） | 试用前有知情说明 |

这六条现在写下来，是因为它们决定了最后三个月是"打磨"还是"救火"。

## 8. 作品集视角：什么让它值得放进去

不是功能多。是这四样：

1. **一个 3 分钟的演示视频**，画面里有一个真人在用，有反应、有失败、有修好。
2. **一张延迟分解图 + 一份 A/B 试用数据**（有身体反馈 vs 纯语音）。这是"研究"的证据，不是"做了个东西"的证据。
3. **一个别人 clone 下来能跑的仓库**：BOM、3D 文件、部署脚本、组装教程。
4. **一段讲得清的"为什么"**：为什么具身比纯语音好、为什么选 Pi 不选 S3、为什么砍掉了 XX。判断力比功能列表值钱。

## 9. 治理：两条负责人，别混

- **项目负责人（李金峰）**：进度、对外沟通、经费、材料提交、和老师对接。
- **技术负责人（你）**：技术选型、接口定义、联调、代码合并。

一个人同时干这两件事，在大二这个阶段基本都会塌一半。分开写清楚，后面不扯皮。

另外三条轻量制度，成本很低但很管用：

- **每周一次 30 分钟站会**：每人三句话——上周交付了什么、这周做什么、卡在哪。产出必须进仓库才算数。
- **决策留痕**：任何"我们决定用 X 不用 Y"，在 `docs/adr/` 写五行（背景/选项/决定/代价/何时重看）。答辩时这些就是你的底气。
- **演示机**：固定一台机器/一张 SD 卡当"演示机"，每次站会都在它上面跑一遍。开发机跑通不算通。

### 【答·你写的那段 PS】

先说一句实话：**你的担心会成真一半。** 团队版的前两个月一定比你一个人做慢，核心代码大概率也是你写得多。这不是你带得不好，是任何四个人从零开始都要付的税。承认它，反而好安排。

但把三件事拆开，就没那么糟：

1. **“做出来”** —— 确实是你出力最多。别对抗这件事，把力气花在让它按计划往前走上。
2. **“谁能讲”** —— 这个可以设计。每条线的人必须能独立演示自己那块；演示不了，就换事，不换人。这样即使代码你写得多，答辩时四个人都有话说——这恰恰是评审想看的。
3. **“一个人能不能做完”** —— 一年期的项目，一个人做，烂尾的概率比团队高得多。团队的第一价值不是“更快”，是“不容易停”。

关于老师那段：**不需要他们懂实现。** 他们的价值是钱、设备、场地、和评审口径。技术决策留在组内，资源需求提给他们。他们评你的不是代码好不好，是“这事有没有做成、有没有数据”——所以要准备的是**可演示 + 可量化**，不是向他们证明你技术强。

至于“他们多久没去过一线”——大概率是真的。但这恰好是你的机会：把一线做出来的东西摆到桌上，比任何争论都有用。
