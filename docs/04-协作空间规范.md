# 04 协作空间规范 v0.1

> 状态：草案（2026-11-10）。这份文件只回答三件事：**仓库怎么分区**、**人和人之间怎么改东西**、**工作台读什么**。
> 它不改 00 的目标，只把 00 第 9 节的"运行方式"落到路径上。
> 一份能跑的结构，胜过一份正确的结构——先照这个跑一个月，再回来改。

---

## 1. 一句话

这个仓库不是代码库，是**四个人的共享工作台**：**权限按路径分配，消息按文件投递，产出按版本合流。**

## 2. 为什么按路径切，而不是按任务切

00 第 9 节已经否掉了"23 件事分给 4 个人"。这里接着否掉另一半：**按任务切目录**（`src/语音`、`src/视觉`）同样会烂。

理由不是分工不好，是 **git 的冲突只发生在文件粒度上**。两个人同时改 `src/audio.py` 相邻的两行，合并时必然要人来判断；而"判断"这件事，现在只有一个人做得来。

按人切目录，把冲突从"内容冲突"降级成"几乎没有冲突"：每个人只写自己的字，合并就是拼接，git 自己就能做完。

一句话：**让冲突在结构上不可能发生，比冲突发生后处理得快更重要。**

## 3. 五个区域

| 区 | 路径 | 谁写 | 谁读 | 干什么 |
|---|---|---|---|---|
| 私有工坊 | `members/<id>/proj/` | 只有本人 | 所有人 | 自己的实现、实验、环境记录 |
| 信箱 | `members/<id>/email/` | **所有人可投递**；只有本人可归档 | 所有人 | 异步沟通留痕 |
| 合流台 | `delivery/` | 只有当班 integrator | 所有人 | 把四个人的东西拼起来跑一遍 |
| 公共典藏 | `docs/`、`tools/` | 改动走 PR | 所有人 | 基线、讲义、ADR、工具 |
| 元规则 | `members/m1/rules/` | 只有本人 | 所有人 | 改流程的提案（暂缓） |

第二行是整份规范里唯一一个"写别人的目录"的地方。它是**投信口，不是共享文档**：只能投新的，不能改旧的。

`rules/` 按你说的先只建在 m1 下面，等第一个月跑完再决定要不要提到顶层。

## 4. 五条不变量

违反任何一条，这套结构就退化成普通的 git 仓库，回到"每次合并都要求人判断"。所以这五条不是建议，是判据。

| | 不变量 | 违反后的症状 |
|---|---|---|
| **I1** | 写域不相交：任意两人的"随手可写集合"交集为空 | 同一个文件两人改，合并要人判断 |
| **I2** | 一文件一消息、只增不改：邮件永不往同一文件里追加 | 两封信同时到，必现 merge 冲突 |
| **I3** | 署名可校验：commit author 与邮件 `from` 一致 | 出问题时找不到人 |
| **I4** | 合流可追溯：delivery 每项都能指回某个 commit | 演示版和源码对不上 |
| **I5** | 单向流动：members → delivery，永不回写 | 合流台变成第二个真源，开始互相覆盖 |

```
UnguaduateProj/

├─ members/
│  ├─ roster.yaml              # 唯一的身份表：id / 姓名 / 主线 / 状态
│  ├─ m1/                      # 李金峰
│  │  ├─ proj/                 # 自己的实现，别人只读
│  │  │  ├─ env.md             # 这台机器怎么装起来的（见第 11 节）
│  │  │  └─ ...
│  │  ├─ email/
│  │  │  ├─ inbox/             # 别人投进来的
│  │  │  └─ archive/           # 自己处理完的（移过来＝已读）
│  │  └─ rules/                # 流程改进提案（暂只有 m1 有）
│  ├─ m2/
│  ├─ m3/
│  └─ m4/
├─ delivery/
│  └─ v0.1-20261215/           # 一次装配
│     ├─ manifest.yaml
│     └─ report.md
├─ docs/                       # 公共典藏（现有 00–03 留在这，别搬）
├─ tools/                      # 工具：ourApp 工作台、build_index、check_scope
└─ data/
   └─ index.json               # 前端唯一入口，脚本生成，人不手改
```

**关于文件夹名**：用 `m1`–`m4`，中文名写进 `roster.yaml`。中文目录名在 URL 里要编码、在 CI 里要加 `core.quotepath=false`、Windows 解压还可能乱码——为了前端好看，不值得在后面每一层都付一次代价。

## 6. 信箱协议

**文件名**：`<日期>T<时分>-<from>-<短码>.md`

```
20261110T2147-m2-power.md
```

带时间和发件人，是为了让文件名本身成为唯一键：四封信落到同一个目录也不会重名，也就不用合并。短码建议用英文或拼音——Windows 下的 git 默认会把中文文件名显示成 `\344\275\240` 这种转义，看着像乱码。

**front-matter**（前端直接吃这一段，不要再去解析正文）：

```markdown
---
id: 20261110T2147-m2-power
from: m2
to: m1
date: 2026-11-10T21:47+08:00
subject: 树莓派供电想确认一下
kind: question          # question | answer | review | notice | handoff
thread: 20261110T0930-m1-003   # 可选，回复哪一封
refs: [a1b2c3d]         # 可选，指到 commit / delivery 版本
---

**我在做什么**：把 Pi 4 的供电改成两路，舵机单独一路。

**卡在哪**：5V/3A 的充电器接上后，摄像头一开就重启。

**想问什么**：BOM 里的 5V/5A 是必须的，还是分路就够了？
```

正文三段，就是 00 第 9 节的"我在做什么 / 卡在哪 / 想问什么"——那套话已经定了，别另起一套。

**已读回执靠移动**：本人读完，把文件从 `inbox/` 移到 `archive/`。工作台的"未读"就是数 inbox 里的文件数，不需要数据库，也不需要点"已读"按钮。

**回复不编辑原信**：新建一封，`thread` 指向原 `id`。邮件是只增不改的日志，不是论坛。

**四种类型够用了**：`question` 提问、`answer` 回答、`review` 给别人产出提意见、`handoff` 交接（我这条线这周交给谁）。

## 7. 合流台

`delivery/` 不放代码副本。它是**一次装配的记录**，不是第二个真源——否则哪天源码和交付版打架，没人知道该信谁（违反 I5）。

```yaml
# delivery/v0.1-20261215/manifest.yaml
version: v0.1-20261215
built_at: 2026-12-15T22:00+08:00
integrator: m1
status: green            # green | yellow | red
members:
  m1: {commit: a1b2c3d, note: 语音链路}
  m2: {commit: e4f5g6h, note: 供电与舵机}
  m3: {commit: 9a8b7c6, note: 延迟打点}
  m4: {commit: 1d2e3f4, note: 讲稿与素材}
checks:
  L0_dialog: pass
  latency_p50_ms: 1750
artifacts:
  - name: demo.mp4
    url: https://...      # 产物不放 git
    sha256: ...
```

`report.md` 只写一件事：这次合流**哪条线断了**、谁去修、什么时候再验。这是"看运作如何"的全部内容。

**大文件不进 git**：>10 MB 的东西（视频、镜像、固件、模型）放 Release 或对象存储，manifest 里写 URL + sha256。git 存二进制会让仓库半年涨到 2 GB，clone 一次十分钟——小白第一次 clone 失败就会放弃。

**合流时发现别人的 bug**：投 `review` 邮件，不改别人代码。真来不及了（比如演示前两小时），owner 口头授权后改，commit message 写 `assist-by: m1 @2026-12-15`（见第 10 节）。

**谁当 integrator**：轮值，一周一人。合流的人才知道接口在哪里对不上；固定让一个人合流，其他人永远学不会"东西怎么装起来"。

## 8. 写权限矩阵

| 路径 | 本人 | 其他三人 | 机器人 |
|---|---|---|---|
| `members/m1/proj/**` | 读写 | 只读 | 只读 |
| `members/m1/email/inbox/**` | 读 + 可归档 | **只能新建** | 只能新建 |
| `members/m1/email/archive/**` | 读写 | 只读 | 只读 |
| `members/m1/rules/**` | 读写 | 只读 | 只读 |
| `delivery/**` | 只读 | 只读 | 读写（当班 integrator 用本人账号） |
| `docs/**` `tools/**` | 走 PR | 走 PR | 读写 |
| `data/index.json` | 只读 | 只读 | 读写 |

## 9. 怎么强制执行（以及为什么先别硬来）

诚实版：**git 没有"目录级权限"这个东西。**

GitHub / Gitea / Forgejo 的 CODEOWNERS、分支保护，都只对 Pull Request 生效。只要允许直接 push 到 `main`，任何人都能改任何文件，服务器拦不住。真想硬隔离，只有一条路：拆成 4 个仓库 + 1 个汇总仓库，用 submodule 串起来。

代价是四个远端、四次 clone、每次更新还要动 submodule 指针——对三个零基础的人来说，这不是"更严格"，是"更早放弃"。

所以分三级，按需往上爬：

| 级 | 手段 | 成本 | 什么时候上 |
|---|---|---|---|
| L0 | 约定 + 人眼 | 0 | 现在 |
| L1 | CI 路径检查 + 机器人邮件 | 半天 | 第一次有人手滑 |
| L2 | 拆仓库 / 全员 PR | 很高 | 不推荐 |

L1 值得提前写，因为顺手：push 之后跑 `tools/check_scope.py`，发现"m2 的 commit 动了 `members/m1/proj/`"，就以 `sys` 身份往两边信箱各投一封 `notice` 邮件。

**不阻断 push**。阻断会让人以为是工具坏了；一封来自机器人的邮件会让人自己意识到"哦，我越界了"。这也正是这套规范自带的价值观：**用消息纠正人，不用权限拦住人。**

## 10. "参与开放"在隔离下怎么落地

00 第 9 节说"参与开放"，第 3 节又规定别人目录只读。这两条会打架，必须给出口，否则会变成"我想帮忙但改不了"的挫败——这比"不让我帮"更伤人。

三个合法姿势：

1. **投建议**：`git diff > patch.txt`，把 diff 贴进邮件正文。
2. **授权代改**：owner 回一句"改吧"，commit 写 `assist-by: m2 @2026-11-12`。授权是**临时的、单次的**，不扩大成长期权限。
3. **自己开实验田**：`members/m2/proj/exp-latency/`，先证明能跑到 1.7 s，再拿数据说服 owner 合并。

第三条最重要：**先做出来，再谈合并**，比"先争权限，再做"快得多，也更符合"参与开放"的本意。

## 11. 微信和仓库的分界线

原来的说法是"工作的事进仓库，个人环境、晚饭、庆功宴进微信"。这条会出事——**环境部署恰恰是 L4 的命根子。**

判断句换成一个：**"这句话，一年后的一个人需不需要靠它把东西重新跑起来？"**

| 内容 | 去哪 | 为什么 |
|---|---|---|
| 装了什么、报什么错、怎么解的 | `members/<id>/proj/env.md` | 演示机重装、换电脑、老师复现，全靠它 |
| 接口约定、参数、延迟数据 | 邮件 / ADR | 是决策和证据 |
| 晚饭、庆功宴、催进度、吐槽 | 微信 | 是情绪和协调 |
| "我今晚不在" | 微信 | 不改变任何人的复现步骤 |

环境记录写多细：**细到一年后的你，照着它能在新机器上一次装通。** 这不是写给别人看的，是写给未来的自己。

## 12. 工作台读什么

前端**不 clone 仓库、不跑 git 命令、不解析文件树**，只 fetch 一个文件：`data/index.json`。

它由 `tools/build_index.py` 从三处生成：

- `members/roster.yaml` —— 人和主线
- `members/*/email/*/` 的 front-matter —— 收件箱、未读数、线程
- `delivery/*/manifest.yaml` —— 版本、状态、延迟数据

三条约束：

1. `data/index.json` **只由脚本写**，人不手改。手改一次，前端和现实就脱节一次，而且每次手改都是一个冲突。
2. 脚本零依赖（标准库 + pyyaml），任何一台机器 `python tools/build_index.py` 就能重建。
3. 前端只读。要改状态，去改源文件。

这条直接决定了第 13 节的选型：**工作台只需要一个能跑 20 行 Python 的常开端点，不需要数据库。**

## 13. 远端怎么放（待会上定）

先给结论：**现在别买服务器；第一次验收前，租一台国内轻量云；Tailscale 不用来承载 git。**

1. **git 的实时性不来自网络层。** 无论 Tailscale 还是公网，`push` 之后别人都得 `pull` 才看得见。真正的实时是：push → webhook → 重跑 `build_index.py` → 工作台刷新。缺的是一个**常开的、能被 webhook 找到的端点**——这才是要花钱买的东西。
2. **Tailscale 是网络，不是服务器。** 免费版（Personal，6 个用户）够四个人用，但它只解决"怎么连上"，不解决"连谁"。没有常开设备，方案就退化成"拿某人的笔记本当服务器"：他一合盖，全组 push 失败。
3. **国内网络是隐性成本。** GitHub 在校园网/移动网络下 push 超时是常态。三个零基础的人遇到一次 `Connection reset`，对 git 的信任就没了。国内轻量云 2 核 2 G 跑 Forgejo + Caddy 足够，一年几百块，比四个人折腾内网穿透的时间便宜。

Tailscale 该用在哪：**从宿舍连实验室里跑实验的机器、连演示机、连数据库面板。** 这些是没有公网 IP 的内网机器，正是它的主场。

定了之后按老规矩写进 `docs/adr/`，五行。

## 14. 迁移步骤

一次提交做完，20 分钟：

1. 建目录：`members/{m1..m4}/{proj,email/{inbox,archive}}`，每层放 `.gitkeep`。
2. 每个成员目录放一份 `README.md`，写清"这里放什么、别人能不能改"。
3. `members/roster.yaml` 填四行：id / 姓名 / 主线 / 状态。
4. `docs/` 不动——它已经是公共典藏，搬一次就是一次冲突。
5. 已有的个人文件 `git mv` 进对应 `proj/`：**一次搬完，以后不再搬。** 路径迁移是冲突最大的来源。
6. 加 `tools/build_index.py`，先生成一份能看的 `data/index.json`。
7. 每个人往别人信箱投一封测试邮件，确认 `pull` 能看到、工作台能显示未读。

然后：**一个月内不改这套结构。** 结构本身频繁变动，比结构不完美更消耗人。
